The problem

An AI assistant is only as useful as what it can find. My notes cover projects, homelab runbooks, research, and personal admin. I wanted Claude and other assistants to search them through the Model Context Protocol (MCP), the same way they'd use any other tool.

The catch is the same one every IT team faces when it connects an AI tool to company data: what can the tool see, and where does that data go? A note about my job search or my finances shouldn't be sent to a cloud model just because it matched a search. So the question wasn't "can I build retrieval?" It was "can I build retrieval where the privacy boundary holds, and prove it?"

How it works

The design is a personal-scale copy of the enterprise knowledge-base pattern Cerebras published: one table, many sources, hybrid retrieval, and thin MCP tools. I adapted it for a single user and added the parts I cared about most: sensitivity tiers, context headers, and evals.

Retrieval

  • Hybrid search. Full-text search (weighted by how rare each term is), vector search, and exact matching on identifiers, fused with reciprocal rank fusion.
  • Context headers. Each chunk is embedded with its note title, folder, heading path, and tags, so a short paragraph still carries where it came from.
  • Incremental sync. Notes are hashed; only changed content is re-embedded. A re-sync with no changes takes 0.3 seconds.
  • Thin MCP tools. search, get_document, list_projects, and kb_stats. The assistant gets small, predictable tools, not raw database access.

The privacy boundary

Sensitivity is a column on every row, not a gate bolted on afterwards. The tier decides which model is allowed to see the text.

publicFine for any model.
personalMine, but not sensitive.
privateStays local. Filtered out of everything the MCP server returns to cloud AI clients.
secretText that matches credential patterns. Never indexed at all.

Deterministic rules set the tier: where the note lives, whether the vault's .gitignore excludes it, and pattern matching for credential-like text. In phase 1, 93 notes were tiered private automatically and one chunk was dropped as secret.

I verified the gate with a question whose answer lives only in a private note. Over MCP it returns no private rows; from the local CLI, the same question finds them. That check is one question today, not a full test suite, and a broader set is on the roadmap.

What I learned: plain full-text search was hurting the hybrid results. Common words were dragging in the wrong notes. Once terms were weighted by rarity, hybrid search found the right note in the top ten every time. Top-1 still trails vector-only search, which is what a reranker in a later phase is for.

A design question I haven't closed

The next phase adds messages and AI session transcripts, and some of that is private. The obvious move is to ask a cloud model whether each item is private. But that sends the item to the cloud first, which leaks exactly what the classifier is meant to protect.

The plan I'm settling on: deterministic local rules decide first (source, path, allowlists, credential patterns); a local model classifies what the rules can't settle; a cloud model only ever sees items already cleared as non-private.

Why this matters for IT work

The same three questions apply to any AI productivity tool or MCP integration a company rolls out:

  • What can it see? Decide sensitivity before data is indexed or shared, not after something leaks.
  • Where does the data go? Know which paths reach a cloud model and filter there.
  • Is it actually working? Measure with a fixed eval set, so "it feels better" becomes a number.

That's how I'd approach evaluating and supporting AI tools for a team: guardrails first, then usefulness, then proof.
